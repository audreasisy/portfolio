1The problem

The company — the Vietnam office of a Japan-headquartered marketing group — moves cash in large, lumpy amounts. Clients pay on 30–90-day terms; KOL and vendor payouts, payroll, tax and intra-group repayments go out on their own schedules. The forecast tracking all of this was one Google Sheet, updated monthly, by hand, by the Chief Accountant and me:

  • every figure was typed — income lines copied from the sales team's deal tracker, recurring expenses re-entered each month, project payouts collected from the Client Success Manager and re-keyed;
  • the view was monthly, because the sales tracker records the month revenue is booked, not the week the cash lands — so an intra-month negative-balance week was invisible;
  • income timing was judged by hand per deal, so payment weeks drifted between updates;
  • the Client Success Manager had no place to enter project payouts — a hidden or protected tab in the finance file would still have exposed the whole forecast.

The Director's brief: a weekly view of cash in, cash out and end-of-week balance for the next six months, refreshed with minimal typing, rough-but-honest (every guess labelled Estimate), with a safe input channel for project payouts.

2What I built

A hub-and-sources architecture: one forecast hub that holds no data of its own and pulls everything, read-only, from the files the owning teams already keep — using only Google Sheets and Apps Script, with no add-ons, external tools or paid services.

  1. Booked income pulls live from the sales tracker. Cash = revenue × (1 + VAT); the payment deadline is derived from the client's timing case; the row lands automatically in the ISO week it's due.
  2. Confirmed receipts pull live from the completion-minute register and are netted against the estimate for the same Order ID — a deal moves from its estimated week to its actual week without ever being double-counted.
  3. Unsigned deals ranked A (90 %) / B (80 %) feed a separate Estimate layer, shown in amber columns so they never contaminate confirmed numbers.
  4. Recurring expenses are typed once — standard amounts and pay rules (which month, which day) in a rule table; every month's rows are formulas.
  5. Project payouts are entered by the Client Success Manager, one row per payment, in their own file, which the hub mirrors read-only.
  6. The weekly engine builds one row per ISO week from 08/2026 to 12/2028 — opening → in → out → closing — with a negative-balance alert and a "lowest weekly closing" line, all on SUMIFS by pay date.

Users type only the blue cells — case overrides, real invoice dates, Received?, the day's FX rate, one-off expenses. Everything else is a formula or a live pull, following one colour key on every tab:

3Key design decisions

  • A separate file is the only real access boundary. Sheets' hidden and protected tabs can still be viewed, so project payouts live in the Manager's own file and enter the hub through a read-only IMPORTRANGE. Access control by architecture, not by tab permissions.
  • One-way pulls; the hub owns nothing. Each source stays the single source of truth for the team that maintains it. Nothing is copied or retyped, so the forecast cannot go stale relative to its inputs.
  • Rule-based income timing, overridable per row. Three client timing cases, with the default resolved from a client → case lookup table. Nothing client-specific is hard-coded in a formula — an early version did that and was replaced.
  • Hybrid forecast, not a switch to the completion register. The first instinct was to forecast from confirmed completion minutes alone, but a completion log can never populate the next six months. I kept the sales tracker as the forward estimate and overlaid confirmed receipts on it, netted by a shared Order ID stamped on every deal and confirmation — the forecast stays whole and sharpens itself as money lands.
  • Real ISO weeks on a multi-year grid. Rejected a fixed "W1–W26" block anchored to launch. Labels use a Thursday-of-week formula so they are year-safe (2026-W53 → 2027-W01) on every Sheets/Excel version; the engine matches by date, so labels are cosmetic.
  • Estimates stay honest. Native currency is kept and converted at viewing time with a typed bank rate and its "as of" date, because the rate at signing is not the rate when money lands. Every constant — VAT rate, opening balance — lives in one config cell.
  • Every structural change is a script, not a browser edit. Seven idempotent Apps Script routines wire the pulls, set up dropdowns and header tags, extend the grid, build the confirmed layer and activate netting. Each snapshots the tab it touches, refuses to run if a tab is missing, and — for netting — aborts if the target formula isn't the exact SUMIFS it expects.

5What I owned end-to-end

I scoped the brief with the Director (requester) and the Chief Accountant (data owner) and set the milestones. I designed the multi-file architecture, the three timing cases, the expense-rule table, the ISO-week calendar and the estimate/confirmed netting model — including the analysis that rejected a full switch to the completion register. I built the live system and its seven Apps Script routines, ran and verified every deployment against backups, and documented it end to end, including a Director walkthrough deck.

Along the way I found and fixed a real-world failure — a header-detection routine that matched an intro sentence containing "pay date" and "week" instead of the actual header, corrupting the Manager file — and turned it into a rule (detection must ignore long prose cells). I also documented the IMPORTRANGE authorisation gotcha that IFERROR silently hides, with its fix, in the runbook.

Two ideas came from stakeholders: the Director asked for the unsigned-deal forecast, and the Chief Accountant's observation about phase payments led me to design the confirmed-receipt layer.

The build used an AI-assisted, pair-programming workflow — I directed an AI coding assistant to my design and spec for formulas, scripts and documentation, then reviewed, ran, tested and debugged everything in the live files. The requirements, architecture and design decisions are mine. No vendor or contractor was involved.
